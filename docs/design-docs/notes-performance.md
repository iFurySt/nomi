# 长文与混排性能

状态：2026-11-01 第一轮实测与优化。关联 [文稿编辑契约](notes-authoring.md) 与 [执行计划](../exec-plans/completed/20261101-long-notes-performance.md)。

## 可重复测试

运行 `pnpm profile:notes`。可用 `NOMI_PERF_LABEL=after` 标记结果；`NOMI_PERF_KEEP_OPEN=1 pnpm profile:notes` 在完成后保留独立窗口用于实际操作。每次生成新的 `.artifacts/notes-performance/<label>-*/`，含隔离 profile、合成 library、report.json、两份 CPU profile 与首屏截图。所有样本只写入该目录，不访问真实文稿库。CPU profile 可导入 Chromium DevTools Performance 面板。

生产 React + 真实 Electron，1360 × 1000 窗口，Mac arm64 / Apple M3 Pro / Electron 44.7.0 / Chromium 152。两个样本：

- `perf.long`：197,001 字符，420 个章节；单个 Markdown 编辑器，表格、块公式、代码与正文混合。
- `perf.mixed`：112,195 字符，60 个 Markdown 块 + 60 个非文本块；包含 6 个交互实验、18 个图片块、36 个文本附件。共 61 个编辑器（含末尾输入区），图片引用同一合成原件。本轮不代表大量不同高清原件、视频或 PDF 的解码压力。

输入使用 Chromium `Input.insertText`，每个样本 21 次单字符输入；计时从 beforeinput 到下一次 requestAnimationFrame。这是主线程响应代理值，不是物理键盘到屏幕像素延迟。输入时同时采集 CPU profile；滚动覆盖全文 30 个位置，每次等待两帧。打开计时为从 Canvas 路由进入文稿直到编辑器出现并再经过两帧，包含轮询误差，**不是冷启动**。长任务从输入阶段开始收集，不含打开阶段。保存检查与编辑器的完整 Markdown 比较，并验证撤销 / 重做和重载。

## 本机结果

同一内容、窗口和输入序列；一次基线、两次优化后采样。下表采用加入完整保存 / 撤销校验后的第二次优化采样；波动属于真实测量结果，不能作为跨设备 SLA。

| 场景 | 指标 | 基线 | 优化后 |
| --- | --- | ---: | ---: |
| 长文 | 输入 P50 | 22.2 ms | 14.1 ms |
| 长文 | 输入 P95 | 24.4 ms | 17.9 ms |
| 长文 | 打开 | 994 ms | 995 ms |
| 长文 | 滚动两帧 P95 | 17.5 ms | 17.8 ms |
| 混排 | 输入 P50 | 11.6 ms | 9.3 ms |
| 混排 | 输入 P95 | 16.7 ms | 13.1 ms |
| 混排 | 打开 | 554 ms | 525 ms |
| 混排 | 滚动两帧 P95 | 17.7 ms | 17.7 ms |

前一次优化采样输入 P95 为 16.9 / 12.5 ms，与上述方向一致。首字最慢约 34 / 39 ms；当前打开成本没有显著改善，不宣称所有交互都能稳定一帧完成。最终采样输入与滚动阶段没有超过 50ms 的 long task；之前混排采样有约 97–100ms 的长任务，所以不承诺零卡顿。

DOM 数量仍为 6,474 / 6,214；没有通过隐藏内容获得输入改善。最终 renderer JS heap 约 104 / 97 MiB（不是进程总内存）。基线未开启 precise memory、数值被量化，**不做内存收益比较**。

独立 `.nomi` 文件包采用真实 `DocumentStore` 和临时磁盘目录，先完整写入，再做 5 次修改 / 保存 / 读取；每次检查整个 DSL 相等：初次建库 6,074ms，保存 P50 / P95 361 / 452ms，读取 P50 / P95 59 / 62ms。读写在主进程异步执行，此数值不含 IPC / UI 保存防抖；renderer 的 `saveDrainMs` 只代表滚动后等待剩余保存与校验，不能当成完整保存耗时。

原始脱敏测量：[基线](../generated/performance/notes-20261101-baseline.json)、[优化后](../generated/performance/notes-20261101-optimized.json)。性能脚本以内容正确性失败为硬失败，延迟先记录趋势；在建立多机重复样本前不加入不稳定的毫秒级 CI 门禁。

## 已实现的优化与不变量

1. 文本事务复制变更块和块列表，复用未变更的笔记、资产、画布与交互程序。完整验证器仍执行，保留容量 / 引用 / 程序校验和原子失败。历史快照按不可变数据使用；调用方必须通过命令更新，不能直接 mutate 返回对象。其他命令仍走完整拷贝路径。
2. Markdown 编辑器用稳定转发回调与 memo 隔离兄弟块更新。回调通过最新 props 执行，避免捕获过期的块 / 文稿。交互块相同程序引用直接通过 memo 比较，其他情况仍做内容比较。
3. 输入时 gutter 隐藏，暂停 transaction / selection / resize 的节点定位；鼠标回来时按当次实际位置恢复。原来每次键入为全文调用 nodeDOM，长篇大量同级节点会重复线性查找。首次鼠标移动必须即时定位，不能落到第一块。
4. 文稿行映射先建立 block ID 索引，避免遍历每个引用时再次扫描全部块。

没有延迟正文事务 / Markdown 保存、没有改输入法和选区语义、没有引入编辑器虚拟化。回归覆盖普通写作、块菜单 / 移动、表格公式、图片附件、IME、撤销重做和保存重开。

## 后续性能边界

当前 DSL 单个 Markdown 上限 200,000 字符、工作区 JSON 上限 2 MiB；本轮测试没有扩大上限，也不代表百万字文稿已支持。下一阶段按实测优先级推进：

- 长文首次解析 / 挂载与 gutter 首次定位仍接近 1 秒，需更细分 trace；不能把虚拟列表直接套在 contenteditable 上破坏选择 / 查找 / IME。
- 初次建立大量正文块文件的开销明显；逐文件持久化、包扫描与事务备份应分别计时，再优化不变文件复用及增量扫描。
- Markdown 序列化与完整 DSL 校验仍随工作区增长。若进一步增量化，必须有全量结果等价测试与落盘完整校验。
- 扩展不同大图片、PDF、多页嵌入、长时间编辑 / 多轮切换和低端设备的内存 / 解码测试；本轮 heap 采样不能用于宣称无泄漏。
